# Ideas Board

A sticky-note idea board for a small team: tilted notes on an infinite canvas,
status by click, buried ideas stay on the wall greyed out. ASP.NET Core 10
Minimal API + Postgres on the server, a framework-free strict-TypeScript bundle
on the client, live updates over SSE. Sign-in by password or GitLab OAuth;
accounts are issued by an administrator, there is no self-registration. The UI
is bilingual (English / Ukrainian).

The notes below — the whole design rationale, measurements and the mistakes
worth not repeating — are in Ukrainian.

By [Alex Pavlyuk](https://github.com/Alex-Pavlyuk) · [Apache-2.0](LICENSE)

---

Дошка ідей команди: закруглені стікери під довільним кутом на нескінченному
полотні, статус змінюється кліком, «поховані» ідеї лишаються на дошці сірими.
Вхід — лише за обліковим записом, який видає адміністратор. UI двомовний:
English / Українська, перемикач у шапці, без перезавантаження.

## Стек і чому саме такий

| Шар | Рішення | Чому |
| --- | --- | --- |
| Бекенд | ASP.NET Core 10, Minimal API | Один процес, один контейнер |
| Дані | **Postgres** | Був SQLite-файл у контейнері — і не пережив жодного викату (див. «Чому не SQLite»). Запити написані руками, без EF Core |
| Дошка | **Strict TypeScript без фреймворка**, esbuild | Див. нижче — це головне технічне рішення |
| Live | **SSE** (`text/event-stream`) | Односторонній потік дрібних JSON-кадрів. Без negotiate, без WebSocket-апгрейду через роутер |
| Авторизація | Cookie-сесії в таблиці + PBKDF2-SHA256 | Відкликання сесії — це `DELETE`, а не blacklist токенів |

### Чому не SQLite

Спершу вся база була одним файлом `/data/ideas.db` у контейнері — для десяти
користувачів це рівно те, що треба, і бекап зводився до копії файлу. Не
спрацювало інше: деплой піднімав кожен реліз **новим** контейнером, а
`VOLUME ["/data"]` без явного `-v` дає Docker анонімний том, свій у кожного
контейнера. Тобто кожен реліз стартував із порожньою базою: ідеї, користувачі й
журнал зникали, а `/api/health` чесно віддавав `"persisted": false` — і цього
рік ніхто не помічав, бо дошка виглядала робочою, просто щоразу порожньою.

Мораль ширша за цей проєкт: SQLite-файл усередині контейнера живий рівно
стільки, скільки живе контейнер. Дані переїхали в Postgres, який не залежить
від життєвого циклу застосунку. EF Core від цього не з'явився: схема — ті самі
шість таблиць, запити ті самі, руками.

### Чому не Blazor Server

Перетягування стікера — це подія на кожен рух миші. У Blazor Server кожна з них
пішла б на сервер по SignalR і повернулася зміною DOM. На дошці з сотнями
стікерів це гарантований лаг, який нічим не лікується. Тому дошка — окремий
статичний острів на TypeScript, який спілкується з бекендом лише через API.

### Чому дошка не гальмує

Дані тримати легко, вбиває **обсяг DOM**: кожен змонтований стікер — це layout,
paint і композитинг на кожному кадрі. Тому:

1. **Один трансформ на все полотно.** Pan і zoom — це одне записування
   `transform` у шар `.world`. Кількість стікерів на це не впливає взагалі.
2. **Просторовий індекс** (рівномірна сітка, `client/src/board/grid.ts`) +
   **точна перевірка AABB** відповідають на питання «що зараз у кадрі» за час,
   пропорційний видимому, а не всьому.
3. **Пул DOM-вузлів:** стікер, що вийшов за екран, від'єднується і його елемент
   перевикористовується наступним.
4. **Рівні деталізації.** Нижче масштабу 0.34 текст усе одно не читається — він
   ховається; нижче 0.17 зникають і тіні.
5. **Перетягування пише напряму в елемент**, оминаючи модель даних; індекс і
   сервер оновлюються лише на відпусканні.

Заміряно на 5401 стікері (M-серія, Chromium):

| | |
| --- | --- |
| Змонтовано вузлів при робочому масштабі | **166** з 5401 |
| Усього DOM-вузлів на сторінці | 570 |
| Style + layout на кадр панорамування | **~0.1 мс** |
| JS heap | ~11 МБ |

Реальні 200–500 ідей — це для такої схеми нічого.

## Перший екран

Аркуш паперу, приклеєний скотчем до дошки, а за ним — сама дошка: справжні ідеї,
нахилені, з паралаксом за курсором і появою по черзі. Єдина тепла поверхня в
усьому застосунку: вона вводить паперову метафору, на якій тримається решта
продукту, і це той екран, якому дозволено бути симпатичним, а не лише
функціональним. Підзаголовок береться випадково з чотирьох варіантів на візит.

Реєстрації немає навмисно: облікові записи видає адміністратор, тож форма питає
лише те, що людині вже вручили.

## Статуси

| # | Ключ | Колір | Хто може ставити |
| --- | --- | --- | --- |
| 0 | Нова / New | жовтий | всі (за замовчуванням при створенні) |
| 1 | Перспективна / Promising | фіолетовий | всі |
| 2 | В роботі / In progress | зелений | всі |
| 3 | Дослідження / Research | блакитний | всі |
| 4 | На паузі / On hold | помаранчевий | всі |
| 5 | Похована / Buried | сірий, 16 % прозорості, розмитий | всі |

**Безповоротно видалити ідею може лише адміністратор.** Решта максимум ховає її
у статус «Похована» — стікер лишається на дошці. Саме тому «поховано» зроблено
статусом, а не видаленням.

**Похована ідея — інертна.** Вона осідає на саме дно дошки:

- знебарвлена, ледь помітна (16 % непрозорості) і трохи розмита — читається як
  глибина, а не як звичайний сірий стікер;
- лежить під усіма живими стікерами (`z-index: 0`), тож ніколи їх не перекриває;
- **її не можна ні перетягнути, ні нахилити.** Перетягування по ній просто рухає
  дошку, ніби її там немає. Правило тримає і сервер: `PATCH /ideas/{id}/position`
  для похованої відповідає `409 idea_buried`;
- при наведенні спливає до читабельних 62 %, а клік відкриває меню статусів —
  інакше її не було б як повернути.

Текст ідеї може редагувати автор або адміністратор.

## Журнал дій і чому він не важитиме гігабайт

Логується: вхід, невдалий вхід, вихід, **відкриття дошки**, створення ідеї,
зміна статусу (старий → новий), редагування тексту, видалення, а також усі дії
адміністратора над обліковими записами.

Три речі тримають обсяг під контролем:

1. **Вузькі рядки.** Подія — це кілька цілих чисел (`ts`, `kind`, `user_id`,
   `idea_id`, `a`, `b`); текст у `meta` пишеться лише там, де без нього подія
   втрачає сенс. Заміряно: **121 байт на подію** разом з усіма чотирма
   індексами. Навіть 5 000 подій на день — це ~210 МБ за рік; реальні для 10
   людей 100–300 подій на день дають **4–13 МБ на рік**.
2. **Переміщення не логуються взагалі.** Возити стікер туди-сюди — найчастіша
   дія і водночас найменш вартісна: це спосіб читати дошку, а не рішення, за
   яке колись відповідати. Рядків цього типу більше не з'являється;
   `EventKind.IdeaMoved = 12` лишається визначеним заради подій, записаних
   раніше, і фільтр у журналі вміє їх показати.
3. **Візити замість пінгів.** «Скільки часу людина провела на дошці» рахується
   не серією heartbeat-подій, а одним рядком у `board_visits`, який
   продовжується. Сорокахвилинна сесія — це один рядок.

**Ретеншн.** Сирі події старші за `LOG_RETENTION_DAYS` (типово 365) щодоби
видаляються — але перед тим кожна подія вже врахована в `event_daily`
(день × тип × користувач). Денні підсумки й записи про візити не видаляються
ніколи, тож майбутній аналітичний дашборд бачитиме всю історію трендів, навіть
коли сирих рядків за той період уже немає.

**Для дашборда пізніше:**
- `GET /api/admin/stats` — агрегати по людях, статусах, обсягу;
- `GET /api/admin/events/export.ndjson` — потоковий експорт сирого журналу
  (не тримає його в пам'яті ні на сервері, ні в браузері);
- або просто читати `event_daily` / `board_visits` з тієї ж бази.

## Запуск

### Локально

Потрібен Postgres. Найпростіше — контейнер, який лишається між запусками:

```bash
docker run -d --name ideas-pg -p 5432:5432 -e POSTGRES_USER=ideas -e POSTGRES_PASSWORD=ideas -e POSTGRES_DB=ideas postgres:17-alpine
```

```bash
dotnet run --urls http://127.0.0.1:5080 -- --DB_PASSWORD=ideas --ADMIN_EMAIL=you@example.com
```

Решта `DB_*` типово вказує саме на такий локальний інстанс
(`127.0.0.1:5432/ideas` під користувачем `ideas`). Схема створюється на старті.

→ http://127.0.0.1:5080 · адмінка на `/admin/`

Пароль адміністратора генерується при першому старті й **один раз** друкується
в лог — далі його не дістати, зберігається лише хеш. `ADMIN_PASSWORD` можна
задати самому, але слабкий буде відхилено (див. нижче) і згенеровано власний —
у логу буде видно, чому.

### Docker

```bash
docker build -t ideas-board . && docker run -p 8080:8080 --add-host=host.docker.internal:host-gateway \
  -e DB_HOST=host.docker.internal -e DB_PASSWORD=ideas -e ADMIN_EMAIL=you@example.com ideas-board
```

Контейнер застосунку не зберігає нічого, тому тому на `/data` більше немає.

### Змінні оточення

| Змінна | Типово | Що робить |
| --- | --- | --- |
| `DB_HOST` | `127.0.0.1` | Хост Postgres. З контейнера в дефолтному bridge база на самому хості — це шлюз `docker0`, а не `127.0.0.1` |
| `DB_PORT` | `5432` | Порт |
| `DB_NAME` | `ideas` | База |
| `DB_USER` | `ideas` | Роль |
| `DB_PASSWORD` | порожній | Пароль ролі |
| `ConnectionStrings__Default` | — | Готовий рядок підключення; перекриває всі `DB_*` |
| `ADMIN_EMAIL` | `admin@local` | Пошта першого адміністратора (лише при першому старті) |
| `ADMIN_PASSWORD` | генерується | Його пароль. Слабкий відхиляється — буде згенеровано інший |
| `LOG_RETENTION_DAYS` | `365` | Скільки тримати сирі події |

## Деплой

Один контейнер за реверс-проксі плюс Postgres. Жодного стану в самому
контейнері — тому його можна перестворювати скільки завгодно разів.

**Що важливо не зламати:**

- `AssemblyName=app` у `IdeasBoard.csproj` → `app.dll`, як чекає `ENTRYPOINT`.
- Контейнер слухає `http://0.0.0.0:8080`; TLS термінує проксі. **Не додавати
  `UseHttpsRedirection`/`UseHsts`** — буде цикл редиректів. Достатньо
  `UseForwardedHeaders`, який уже налаштований.
- `wwwroot/app/*` мусить бути закоміченим: у білд-стейджі немає Node.
- База має бути створена заздалегідь (роль + порожня база). Застосунок сам
  робить лише `CREATE TABLE IF NOT EXISTS` — права власника бази йому вистачає,
  суперюзер не потрібен.

### Змінні оточення в проді

| Змінна | Обов'язкова | Значення |
| --- | --- | --- |
| `ADMIN_EMAIL` | так | пошта першого адміністратора |
| `ADMIN_PASSWORD` | так | **від 14 символів** (`PasswordPolicy`) |
| `DB_HOST`, `DB_PASSWORD` | так | де Postgres і під яким паролем роль |
| `DB_PORT`, `DB_NAME`, `DB_USER` | ні | `5432`, `ideas`, `ideas` |
| `GITLAB_URL`, `GITLAB_CLIENT_ID`, `GITLAB_CLIENT_SECRET` | для SSO | див. розділ «Вхід через GitLab» |
| `GITLAB_REDIRECT_URI` | ні | якщо автовизначення origin не підходить |
| `GITLAB_AUTO_CREATE` | ні | `true` — перший вхід через SSO сам заводить запис. Типово вимкнено |
| `GITLAB_ALLOWED_DOMAINS` | ні | обмежує автостворення доменами пошти. Без нього `GITLAB_AUTO_CREATE=true` впускає **будь-кого** з вашого GitLab |
| `PUBLIC_ORIGIN` | ні | перекриває визначення схеми й хоста |
| `LOG_RETENTION_DAYS` | ні | типово 365 |

⚠️ `ADMIN_PASSWORD` треба задати **до** першого запуску на порожній базі.
Інакше пароль згенерується і один раз потрапить у лог — більше ніде він не
зберігається.

⚠️ Якщо секрети приходять із CI, тримайте `DB_*` окремими змінними, а не одним
рядком підключення: значення з `;` часто не піддається маскуванню в логах.

### Чи пережили дані викат

```bash
curl -s https://<ваш-хост>/api/health
# {"status":"ok","database":"ok","persisted":true,"bootedAt":1788…}
```

`persisted` означає «схема вже існувала, коли процес стартував». `false` одразу
після деплою — це або перший запуск, або хтось видалив базу; на працюючому
стенді там завжди `true`. `database` показує стан з'єднання: якщо Postgres
недоступний, застосунок однаково піднімається і пише сюди причину, замість
мовчазного 502 (див. `Program.cs`).

### Бекап

```bash
pg_dump -h <host> -U ideas ideas > ideas-$(date +%F).sql
```

Дамп — повний бекап: ідеї, користувачі, журнал.

## Паролі

Реєстрації немає — облікові записи роздає адміністратор. Порожнє поле пароля в
адмінці означає «згенерувати»: 4 групи по 4 символи для звичайного користувача,
5 груп для адміністратора (`abcd-efgh-jkmn-pqrs-tuvw` — 20 випадкових символів з
алфавіту на 31 знак, ~99 біт). Пароль показується **один раз**, далі в базі лише
PBKDF2-SHA256 (210 000 ітерацій).

Пароль, введений руками, перевіряється (`Services/PasswordPolicy.cs`):

| Правило | Чому |
| --- | --- |
| ≥ 10 символів, **≥ 14 для адміністратора** | адмін може безповоротно видалити будь-яку ідею і прочитати весь журнал — це єдиний обліковий запис, який варто атакувати |
| не зі списку очевидних | звірка після зрізання цифр і пунктуації, тож `Admin123!` ловиться так само, як `admin` |
| ≥ 6 різних символів, не суцільний ряд | `aaaaaaaaaaaa` і `abcdefghij` проходять будь-яку перевірку довжини |
| не містить локальну частину пошти | перше, що спробують після списку очевидних |

Зміна пароля **розлогінює всі живі сесії** цього користувача (`UserStore.SetPassword`).

## Вхід через GitLab

Звичайний authorization code flow: `state` проти CSRF, потім `/api/v4/user` по
профіль. Працює і з gitlab.com, і з self-hosted інстансом.

**Поки `GITLAB_*` не задані — фічі просто немає.** `/api/auth/providers` віддає
`{"gitlab":false}`, кнопка на екрані входу не малюється, а обидва SSO-маршрути
відповідають редіректом `/?sso=unconfigured`. Ніякої напівувімкненої кнопки, яка
може лише зламатися.

### Налаштування

У GitLab: **User settings → Applications** (або Admin → Applications, якщо
застосунок має бути спільним для всього інстансу), scope `read_user`, redirect URI —
`<адреса застосунку>/api/auth/gitlab/callback`.

| Змінна | Обов'язкова | Що це |
| --- | --- | --- |
| `GITLAB_URL` | так | напр. `https://gitlab.com`, без слеша в кінці |
| `GITLAB_CLIENT_ID` | так | Application ID |
| `GITLAB_CLIENT_SECRET` | так | Secret |
| `GITLAB_REDIRECT_URI` | ні | якщо порожня — будується з публічного походження (див. нижче) |
| `PUBLIC_ORIGIN` | ні | напр. `https://board.example.com` — задавати лише якщо автовизначення не підходить |
| `GITLAB_AUTO_CREATE` | ні | `true` вмикає створення облікових записів (див. нижче), типово `false` |
| `GITLAB_ALLOWED_DOMAINS` | ні | напр. `example.com,example.org` — обмежує автостворення доменами пошти |

Локально:

```bash
dotnet run --urls http://127.0.0.1:5080 -- \
  --GITLAB_URL=https://gitlab.com \
  --GITLAB_CLIENT_ID=... --GITLAB_CLIENT_SECRET=...
```

⚠️ Secret — у змінні оточення або в CI/CD variables, **не** в `appsettings.json`:
цей файл у git.

### Схема (http чи https) визначається хостом

За реверс-проксі контейнер бачить звичайний http, і схема клієнта до нього не
обов'язково доїжджає: на одному зі стендів навіть вручну надісланий
`X-Forwarded-Proto: https` повертався як http. Тому `Services/PublicUrl.cs`
вважає TLS усе, що не loopback, і саме звідти беруться і `redirect_uri`, і
прапорець `Secure` на куках.

Без цього ламалися дві речі: GitLab отримував `http://…/callback` і відхиляв вхід
(redirect_uri звіряється точно), а сесійна кука їхала без `Secure`. Якщо стенд
влаштований інакше — задайте `PUBLIC_ORIGIN`.

### Чому SSO типово НЕ створює облікові записи

Поширений варіант — заводити запис кожному, хто зайшов через SSO. Для порталу,
куди має потрапити вся організація, це правильно. Для дошки на десять осіб — ні:
вся модель доступу тримається на тому, що **облікові записи видає
адміністратор**, реєстрації немає навмисно. Якби SSO створював записи сам,
будь-хто з вашого GitLab (включно з підрядниками й зовнішніми учасниками
проєктів) опинився б на внутрішній дошці. Тому типово `GITLAB_AUTO_CREATE=false`,
і вхід через GitLab лише **прив'язується** до вже наявного запису.

Порядок пошуку в колбеку:

1. за `gitlab_id` — звичайний випадок після першого входу;
2. за поштою (власною або раніше прив'язаною) → прив'язує GitLab до цього запису.
   Саме це дає SSO обліковим записам, які адміністратор завів руками: нікому не
   треба нічого «підключати»;
3. якщо `GITLAB_AUTO_CREATE=true` і домен пошти дозволений — створює запис
   (звичайний користувач, не адміністратор);
4. інакше — `/?sso=no_account` і повідомлення «попросіть доступ в адміністратора».

Якщо вам потрібна поведінка «кожен зі свого GitLab заходить сам» —
`GITLAB_AUTO_CREATE=true`, і майже завжди разом із `GITLAB_ALLOWED_DOMAINS`.

### Що ще перевіряється

- **Заблокований у GitLab** (`state != "active"`) не заходить, навіть якщо токен
  ще живий.
- **Вимкнений на дошці** (`is_active = 0`) не заходить теж.
- **Чужий GitLab** не можна прив'язати до запису, якщо він уже належить іншому —
  `/?sso=link_taken`.
- **`state`** живе в httpOnly-кукі з `Path` на сам колбек і 10-хвилинним строком,
  звіряється constant-time і одноразовий. `SameSite=Lax`, а не `Strict`, інакше
  кукі не пережила б повернення з GitLab.
- **Успішний SSO знімає блокування перебору** для цього запису: GitLab щойно
  довів, кому належить обліковий запис, тож тримати справжнього власника за
  дверима через чужі спроби підбору немає підстав.

Кожна невдача пишеться в журнал як звичайний невдалий вхід із причиною
(`gitlab:no_account nobody@elsewhere.com`), тож зламане SSO видно там само, де
все інше.

### Керування

Вкладка «Користувачі» в адмінці показує прив'язаний акаунт тегом `@username` і
кнопку **Відв'язати GitLab** — обліковий запис і пароль при цьому лишаються.
Окремої сторінки профілю з «підключити GitLab» тут немає: прив'язка відбувається
сама при першому вході за збігом пошти.

## Захист від перебору

`Services/LoginGuard.cs` — експоненційна затримка, окремо по обліковому запису і,
як підстраховка, по адресі джерела. Лічильники лежать у базі, а не в пам'яті:
рестарт контейнера не має бути безкоштовним скиданням для того, хто підбирає.

| | Обліковий запис | Адреса джерела |
| --- | --- | --- |
| Безкоштовних спроб | 5 | 30 |
| Далі | 30 с → 1 хв → 2 хв → 4 хв → 8 хв → 16 хв | те саме |
| Стеля | 30 хв | 5 хв |

Чому затримка, а не жорстке блокування: постійний лок — це готовий DoS. Досить
п'ять разів помилитися на адресу директора, і він не зайде на власну дошку.
Подвоєння робить підбір безнадійним (десяток невірних відповідей коштує пів
години за спробу), а людина, яка просто забула пароль, повертається за хвилину.

Деталі, які мають значення:

- **Перевірка йде до звіряння пароля.** Заблокована спроба коштує зловмиснику
  раунд-тріпу, а не 210 000 ітерацій PBKDF2 нашого CPU. І правильний пароль не
  відчиняє заблокований запис — у цьому й сенс блокування.
- **Стукати під час блокування марно, але й не гірше:** лічильник не росте,
  поки лок діє; ескалація відбувається на наступній невдачі після його
  завершення.
- **Скидання:** правильний пароль обнуляє лічильник запису; година тиші обнуляє
  будь-який. Лічильник джерела свідомо **не** скидається успішним входом —
  інакше один валідний запис став би важелем для обнулення підстраховки.
- **Однаковий час відповіді.** Невідома адреса звіряється з фіктивним хешем
  (`UserStore.DecoyHash`), інакше зловмисник перебирав би самі лише адреси за
  часом відповіді.
- **`Retry-After`** віддається в заголовку і в тілі, тож форма показує зворотний
  відлік, а не абстрактне «спробуйте пізніше».
- **Зняти блокування** може адміністратор — вкладка «Користувачі», кнопка біля
  заблокованого запису. Блокування адреси зняти не можна, але воно саме спадає
  максимум за 5 хвилин.

Поверх цього лишається пропускний ліміт ASP.NET на `/api/auth/login` (30 запитів
за хвилину з адреси) — він просто не дає залити ендпоінт, поки `LoginGuard`
робить точну роботу.

Що видно адміністратору: вкладка «Користувачі» — стан блокування і кнопка зняття;
«Статистика» — картка «Захист входу» (невдалі входи, спрацювання, скільки
заблоковано зараз); «Журнал дій» — кожна невдала спроба з адресою, момент
блокування з його тривалістю і зняття блокування.

## Клієнтський бандл

`wwwroot/app/*` **закомічений** — у Docker-стейджі немає Node, тож збірка образу
не вміє зібрати фронтенд сама. Після правок у `client/src`:

```bash
cd client && npm ci && npm run build
```

або разом зі збіркою .NET: `dotnet build -p:BuildClient=true`.
Перевірка типів: `cd client && npm run typecheck`.
